# US-102 — Request a Return with eligibility rules and Refund calculation

## User story

As a **Customer**,
I want to return specific quantities of items from a delivered Order within 30 days,
so that I get an immediate answer and know how much will be refunded.

## Scope

This story adds the `returns` and `return_lines` tables, `POST /returns`, the eligibility rules (FR-4), the Denial Reasons (FR-5) and the Refund calculation (FR-8). It also starts filling `quantity_returned` and `returns[]` in the order lookup from US-101.

**Not in this story:** Restock and the inventory view (US-103), and viewing a single Return (US-103).

## Acceptance criteria

**AC-1 — Accepted return**
**Given** an Order delivered 12 days ago (FixedClock), with a returnable Line Item bought at 19.99 × 3
**When** `POST /returns` is sent with `{order_id, email, lines: [{sku, quantity: 2}]}`
**Then** the response is 201, containing `return_id` (matching `RET-` + 12 hex), `order_id`, `lines`, `refund_amount: "39.98"` and `created_at` (UTC, ending in `Z`).

**AC-2 — Window boundary**
**Given** an Order with Delivery Date D
**When** a return is requested with today = D + 30
**Then** it is accepted
**And** with today = D + 31, it is denied with 422 `RETURN_WINDOW_EXPIRED`.

**AC-3 — Denial reasons**
**Given** each of the following invalid requests
**Then** each returns 422 with `error.code` equal to:
- `ORDER_NOT_DELIVERED` — a `shipped` Order or a `cancelled` Order
- `ITEM_NOT_ON_ORDER` — a SKU that is not on the Order
- `ITEM_NOT_RETURNABLE` — a Product with `returnable = false`
- `QUANTITY_EXCEEDS_RETURNABLE` — a quantity greater than purchased − already returned
- `INVALID_REQUEST` — empty `lines`, a duplicate SKU, or a quantity below 1

**AC-4 — Unknown Order or wrong email**
**Given** an unknown Order ID or a wrong email
**When** a return is requested
**Then** the response is 404 `NOT_FOUND`, identical to the order lookup's 404.

**AC-5 — All-or-nothing**
**Given** a request with one line that is not on the Order and another line that is not returnable
**When** it is submitted
**Then** it is denied with `ITEM_NOT_ON_ORDER`, because AD-12 checks each rule across all lines before moving to the next and the first failing rule wins
**And** no `returns` or `return_lines` rows exist for it.

**AC-6 — Multiple Returns**
**Given** a Line Item with quantity 2
**When** 1 unit is returned, then 1 more unit, then 1 more
**Then** the first two requests return 201 and the third returns 422 `QUANTITY_EXCEEDS_RETURNABLE`
**And** `GET /orders/{id}` shows `quantity_returned = 2` and two entries in `returns[]`.

**AC-7 — Money**
**Given** the refund function
**Then** it uses `Decimal` with `ROUND_HALF_UP` to 2 decimal places
**And** `refund_cents` is stored as an INTEGER
**And** the refund is never recalculated when the Return is read back.

**AC-8 — Audit**
**Given** an accepted Return
**Then** a `RETURN_REQUESTED`/`accepted` event and a `REFUND_CALCULATED` event are written in the same transaction as the Return.

**Given** a denied request (including `INVALID_REQUEST`, and not-found with `denial_reason: null`)
**Then** exactly one `RETURN_REQUESTED`/`denied` event is written and committed before the error response, with the `denial_reason` in its details
**And** a request with missing fields or wrong types gives 422 `INVALID_REQUEST` from the schema and is not audited.

**And** no audit event contains an email.

**AC-9 — Quality**
- `pytest` passes, with domain + services coverage ≥ 90%.
- The eligibility and refund functions in `domain/` have unit tests for every rule and for the boundary.

## Dev tasks

1. Add `returns` and `return_lines` to `repositories/schema.sql`. Add seed fixtures to `seed.py` only if a test needs them, without changing existing rows (AD-10).
2. `domain/eligibility.py`: `check_eligibility(order, lines_requested, returned_quantities, products, today) -> None | DenialReason`. It implements AD-12 rules 2–7 in order; rule 1 is the service's lookup.
3. `domain/refund.py`: `calculate_refund(lines) -> Decimal`, using `domain/money.py`.
4. `ReturnRepository`: `insert_return`, `insert_lines` and `list_for_order(order_id)`. Replace the `returned_quantities(order_id)` stub with the real SUM query (AD-9, single owner).
5. `ReturnService.request_return(cmd)`. Inside one `uow.transaction()`:
   - load the data and `returned_quantities`
   - check eligibility using `clock.today()`
   - **if eligible:** insert the Return and its lines, and audit `RETURN_REQUESTED`/`accepted` and `REFUND_CALCULATED`
   - **if denied or not found:** audit `RETURN_REQUESTED`/`denied`, commit, and only then raise (AD-4)
6. Update `OrderService.lookup` to fill `quantity_returned` and `returns[]` from `ReturnRepository`.
7. API: `POST /returns` with type-only Pydantic schemas `ReturnRequest`, `ReturnLineIn` and `ReturnView` (AD-12). Map the `ReturnDeniedError` reason to 422 `error.code`, and document the 201/404/422 responses in OpenAPI.
8. Tests:
   - unit tests for each eligibility rule and the boundary (FixedClock)
   - unit tests for refund rounding
   - API tests for AC-1 to AC-6
   - audit assertions for AC-8
9. QA: create `docs/qa/gates/US-102.yml` with status PASS.
