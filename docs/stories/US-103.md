# US-103 — Restock Inventory on Return, view Inventory and view a Return

## User story

As a **Customer**,
I want my returned items put back into stock and my Return retrievable later,
so that the Return is fully processed and I can check its details at any time.

As **Support Staff**, I want Inventory changes to be visible through the API and audited.

## Acceptance criteria

**AC-1 — Restock**
**Given** `SKU-SCARF` with `quantity_on_hand = 10`
**When** a Return of 2 × `SKU-SCARF` is accepted
**Then** `GET /inventory/SKU-SCARF` returns 200 `{sku, name, quantity_on_hand: 12}`.

**AC-2 — Atomic with the Return**
**Given** a failure injected in the Restock step (test double)
**When** a Return is requested
**Then** no `returns` row, no `return_lines` row, no Inventory change and no success Audit Events are stored.

**AC-3 — No double-claim**
**Given** a Line Item with 1 unit left to return
**When** two return requests for 1 unit run concurrently (two threads, same app)
**Then** exactly one returns 201 and the other returns 422 `QUANTITY_EXCEEDS_RETURNABLE`
**And** Inventory increases by exactly 1.

**AC-4 — Denied return does not restock**
**Given** any denied return request
**Then** Inventory is unchanged.

**AC-5 — Restock audit**
**Given** an accepted Return with N Return Lines
**Then** exactly N `INVENTORY_RESTOCKED`/`recorded` events (one per Return Line, each with `sku` + `quantity`) are written in the same transaction as the Return.

**AC-6 — View a Return**
**Given** an existing Return
**When** `GET /returns/{return_id}` is called with the matching `X-Customer-Email`
**Then** the response is 200 with `return_id`, `order_id`, `lines`, the stored `refund_amount` and `created_at`
**And** an unknown Return ID or a wrong email gives an identical 404 `NOT_FOUND`
**And** each attempt writes one `RETURN_VIEWED` event (`found` or `not_found`).

**AC-7 — Unknown SKU**
**When** `GET /inventory/SKU-NOPE` is called
**Then** the response is 404 `NOT_FOUND`.

**AC-8 — Quality**
- `pytest` passes, with domain + services coverage ≥ 90%.

## Dev tasks

1. `ProductRepository.add_inventory(sku, qty)`, the only Inventory write path, which asserts `uow.in_transaction`, and `get(sku)`.
2. Extend the existing `ReturnService.request_return` transaction: after inserting the lines, restock each line and audit `INVENTORY_RESTOCKED` before the commit. Never open a second transaction, because a nested one raises (AD-3).
3. `InventoryService.get(sku)` (an entry point with its own read transaction), plus the `GET /inventory/{sku}` router and the `InventoryView` schema.
4. `ReturnService.get(return_id, email)`, which checks the email against the parent Order, raises the same `NotFoundError` for a missing Return or a wrong email, and audits `RETURN_VIEWED`. Add the `GET /returns/{return_id}` router.
5. Tests:
   - AC-2: monkeypatch the repository to raise
   - AC-3: `threading` with two TestClient calls
   - API tests for AC-1, AC-4 to AC-7
6. QA: create `docs/qa/gates/US-103.yml` with status PASS.
